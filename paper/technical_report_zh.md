# AstraBuild：基于证据约束智能体的变电站部件级数字孪生重建

**版本：** 技术报告草案 v0.2
**研究站点：** 匿名运行中变电站
**研究终点：** D41
**主体几何基线：** D38.2；D40 为几何保持不变的材质展示层；D41 为巡检语义附件增强层

> **实验配置来源说明**：项目负责人确认本轮长期重建使用 **Codex + GPT-6 Astra + Extra High 推理强度**。检查 `experiments/blender-substation` 历史批次后，没有发现模型名称和 reasoning effort 被写入旧 batch manifest。因此本文把这一项标记为**项目负责人确认的实验元数据**，不把它伪装成能够由旧日志独立恢复的 provenance。新版发布目录已把这项信息冻结进 `release/experiment_manifest.json`。

## 摘要

本文研究的不是“一次性从图片生成一个三维模型”，而是一个更接近工业数字孪生的问题：**通用推理智能体能否在缺乏厂家 CAD、缺乏独立测绘真值、现场图像覆盖不均和语义台账并不等价于真实几何的条件下，长期操作一套重建工程，把粗模逐步转化为可编辑、可复用、可验证、可挂接巡检语义的部件级模型？**

我们将这套流程抽象为 AstraBuild：

`证据编译 → Codex/GPT-6 Astra 推理 → Blender/Python 动作 → 确定性验证 → 不可变历史 → 再规划`。

智能体负责理解证据、形成几何/语义假设、编写构建脚本和在失败后重新设计方案；它**不拥有“结果正确”的最终判定权**。建模结果必须经过保存后重读、历史对象保持、输入文件哈希、实例刚性、BVH 表面对照、落地/承托/接续、相机取景、覆盖审计等独立检查。失败批次、返工版本和局限声明都保留下来，成为后续推理的外部记忆。

现有技术总账记录 D38 前 **38 个核心重建批次**，对应 54 个 build 脚本、58 个 validate 脚本、150 个 manifest、71 个 validation JSON、28 版安装队列和 109 个局部粗模参考 NPZ。D38.2/D40 等价几何规模为 **37,153 个对象 / 755 个场景 / 858 个集合 / 3,916 个 mesh datablock / 约 2,999 万顶点**。1,550 条当前表面对照记录的 median/p90/p95 为 **0.036/0.084/0.116 m**。**这些数值是相对于同一个摄影测量粗模的内部几何对照，不是独立测绘精度。** 5 cm 筛查账本保留 149 个通过项与 101 个未通过项，并不把后者删除或改判。

在 B25/B26 的选定高区覆盖审计中，距已建模型大于 1 m 的粗模样本比例从 **78.8% 降到 14.6%**；GIS-B 和主变高区中位距离分别从 **8.12→0.15 m**、**3.15→0.06 m**。这组指标的意义是发现“台账看起来完成但空间上仍有大块未解释结构”的遗漏，而不是宣称全站绝对精度。

本文进一步分析 B01→B02、B15、B36、D38 和语义 v3 等案例。它们表明可靠性并不是“模型第一次就猜对”，而是**错误能否被另一层证据发现、错误历史能否保留、失败能否改变后续测量协议或组件抽象**。D41 最终把 79 个附件网格、17 类此前缺失的巡检相关部件，以共享附件 MASTER 的形式并入 T1/T2 两台主变，并保存世界坐标/巡视点位映射。

因此本文的核心结论不是“GPT-6 Astra 能全自动、测绘级地重建变电站”，而是：在明确证据边界、确定性执行器、不可变工程历史、分层 verifier 和稀疏人工反馈的共同约束下，通用推理模型可以成为一个有价值的**长时程三维重建操作智能体**。

# 1. 研究问题

我们参照 GPT-Policy、GPT-6 Astra embodied-policy 技术报告以及 RoboDojo 一类评测报告的组织方式，不先从“效果图”讲起，而是先明确五个研究问题。

**RQ1 — 结构化重建：** 粗模、现场图像和台账能否被转化为可编辑、可复用、具有组件层级的 Blender 场景，而不是一张不可编辑的融合表面？

**RQ2 — verifier 约束可靠性：** 独立验证能否发现“看起来合理但证据不成立”的几何，并迫使系统修改测量方法、参数乃至组件抽象，而不是静默接受？

**RQ3 — 覆盖度驱动补全：** 当“台账设备已经基本做完”时，粗模占据/距离审计能否发现仍未被解释的空间结构，并改变后续任务选择？

**RQ4 — 人类可引导纠错：** 人工只提供红框、俯视漏建位置或“这两个设备同构”这样的高层信息时，智能体能否完成后续证据搜索、坐标求解、构建和验证，而不要求用户进入 Blender 逐顶点操作？

**RQ5 — 巡检语义：** 已稳定的几何能否在不破坏早期历史的前提下，继续挂接设备/部件/巡视点位语义？

# 2. 与参考机器人工作的对应关系

GPT-Policy 的关键结构不是“VLM 直接控制机器人”，而是把任务上下文、视觉/历史证据、VLM 的 tool request、受约束执行和执行反馈明确拆开。GPT-6 Astra embodied-policy 报告则进一步强调 System-2 语义推理和低层动作先验之间的分工，并用总体指标、per-task 表、行为视频和失败机制共同描述结果。RoboDojo 风格的报告强调清晰的任务集合、分母、得分口径和限制。

AstraBuild 使用同样的**科研表达框架**，但对象不是机器人动作，而是持续存在的三维工程：

| 机器人闭环 | AstraBuild |
|---|---|
| camera / proprioception | 照片 / 粗模 / 台账 /历史工程 |
| VLM policy / System 2 | Codex + GPT-6 Astra 推理 |
| EEF / tool request | Blender/Python 建模动作 |
| controller / simulator | Blender 几何执行器 |
| safety / execution checks | 哈希、重读、刚性、BVH、接触、覆盖 verifier |
| action outcome | 新 blend / validation JSON / review render |
| interaction history | 不可变 batch 历史 |
| human cue | 俯视标注、等价授权、语义审查 |

这里最重要的类比是：**高层“知道应该做什么”和低层“可靠地把它做对”是两种不同能力。**

![图 1：AstraBuild 智能体闭环](../figures/fig01_agentic_loop.png)

图 1 把研究方法从“AI 帮我写 Blender 脚本”提升为一个可分析的闭环：证据编译器控制输入，模型提出动作，确定性 actuator 修改工程，verifier 决定是否接受，失败和限制回到下一轮上下文。

# 3. 数据与证据角色

## 3.1 摄影测量粗模

粗模由 23 个注册瓦片构成，约覆盖 112 m × 134 m。它在本项目中承担三种角色：

1. 全站布局/相对位置基准；
2. 局部设备拟合与表面对照参考；
3. 后期发现“大块未解释占据”的 coverage sensor。

但粗模自身有破洞、拉伸、融合邻台和局部缺失，因此它不能同时被当作“输入参考”又被无条件称为“独立真值”。本文所有厘米级 surface residual 都保留这一限制。

## 3.2 无人机与地面照片

早期安装队列统计约 775 张 identity-photo 候选，后续 photo-audit 还持续增加局部证据。照片主要支持：

- 可见部件形态；
- 重复数量和部件顺序；
- 接触/支撑/朝向关系；
- 材质和颜色；
- “旧模型里这个位置是否真的有设备”的人工复核。

但部分阶段相机标定不完整，照片本身也不能保证铭牌级身份认证，因此本文不把所有图像都包装成统一的 metric reprojection benchmark。

## 3.3 设备台账、12MZ 与 UE 盒

历史报告总结：153 台登记设备、106 个官方名称、1,842 行 12MZ 编码记录，以及 82 个 UE4 手工位置盒。这些数据提供名称、清单、语义和位置先验，但存在一个重要区别：**台账中有某个设备，不代表场景中已经存在正确几何；一个空间盒靠近某个物体，也不代表身份一定正确。**

后续 semantic v3 的返工恰好说明，仅靠字符串或最近空间盒会把跨间隔母线、避雷器、接地刀闸等挂错。

## 3.4 人工审查与 batch 历史

人工反馈不是“算法失败后的临时补丁”，而是方法的一种正式输入。B08 的两台主变同构授权、B36 的俯视漏建、D38 的红框和后续语义审查都进入工程历史。

batch 文件系统同时承担长期外部记忆：continuation、plan、builder、validator、manifest、失败 traceback、review media、limitations 都能被后续回读。

# 4. 方法：Evidence-Grounded Closed Loop

把第 \(t\) 个阶段的持久状态写成

\[
S_t=(M_t,A_t,X_t,Q_t),
\]

其中 \(M_t\) 是场景几何，\(A_t\) 是组件库/实例层级，\(X_t\) 是设备/部件/巡检语义，\(Q_t\) 是 provenance 与验证历史。

证据编译器从粗模 \(G\)、图像 \(I\)、工程记录 \(R\)、空间先验 \(U\) 和历史 \(H_t\) 中抽取当前上下文：

\[
C_t=\mathcal C(G,I,R,U,H_t).
\]

推理智能体提出结构化动作：

\[
a_t\sim\pi_\theta(\cdot\mid C_t,S_t,f_{t-1}),
\]

动作由 Blender/Python 执行器 \(E\) 实际运行，再交给 verifier \(V\)：

\[
(\tilde S_{t+1},e_t)=E(a_t,S_t),\qquad v_t=V(\tilde S_{t+1},G,Q_{\le t}).
\]

只有通过当前批次相关检查的产物才进入下一版；否则失败原因也作为新的上下文。

## 4.1 动作不是“直接输出 mesh”

本项目成熟阶段的典型动作更接近工程 API：

- 从粗模裁取局部参考并保存 source origin；
- 构建参数化组件 MASTER；
- 用刚性 site transform 实例化；
- 生成母线、跳线、连接件、支架等现场几何；
- 拆分 variant 或把不该共享的段从 MASTER 移出；
- 生成 clean / overlay / reference 审查场景；
- 计算 BVH residual、落地/接续/承托、coverage；
- 把错误对象隔离到 quarantine；
- 保存不可变版本和 manifest。

这使系统更接近“智能体编写并操作工程程序”，而不是黑盒 text-to-mesh。

## 4.2 组件库是一条可证伪假设

`MASTER → SITE instance → FULL_STATION_REVIEW` 不是单纯的内存优化，而是把“这些设备应当同形”编码成显式假设。B08 在用户授权两台主变可共享后建立总成；B15 则证明，如果现场证据说明某段母线只属于特定位置，就必须把它从共享 MASTER 拆出。

## 4.3 verifier 是分层的

![图 2：验证栈](../figures/fig08_validation_stack.png)

一张 blend 能重新打开，只能证明文件层正常；矩阵能复现，只能证明数值层正常；BVH residual 低，只能证明对某个参考表面一致；这些都不能自动证明身份正确、全站完整或达到测绘级精度。

历史验证至少包含：

1. 历史对象/场景/集合保持；
2. site matrix 保持；
3. 受保护输入 SHA-256；
4. asset save/reopen round trip；
5. finite geometry；
6. manifest 数值复现；
7. BVH 表面对照；
8. 落地/承托/端点接续；
9. 相机取景/非空渲染；
10. SVD 刚性与正行列式；
11. occupancy/coverage 审计。

# 5. 长时程研究设计

这 38 个核心批次不是 38 次独立实验。后一个 batch 会继承前一个 batch 的模型，还会继承/修改测量协议，因此这是典型的**纵向系统研究**。

![图 3：长期演化时间线](../figures/fig02_longitudinal_study.png)

可以把过程分为六个阶段：

| 阶段 | 批次 | 主要变化 |
|---|---|---|
| 设备拟合试验 | B01–B05 | 建立“软件通过 ≠ 几何通过”；B01 失败催生新 holdout 规则 |
| 层级形成 | B06–B10 | 土建、双主变、电容器；形成本地 MASTER + site instance |
| GIS/设备族扩展 | B11–B19 | 跨批复用、变体分离、共享边界返工 |
| 连接系统 + 覆盖度 | B20–B30 | 母线、耐张串、跳线；coverage 开始决定下一步建什么 |
| 收口 + 人工纠错 | B31–D38 | 土建/小设施；B36/D38 形成完整 human-in-loop 纠错链 |
| 展示 → 巡检语义 | D40–D41 | D40 材质不改几何；D41 增加巡检附件/世界坐标 |

历史总账还记录 54 build、58 validate、150 manifest、71 validation JSON、28 版安装队列、109 个局部粗模参考 NPZ 和 719 个新审查场景。这些是“工程历史规模”，不是统计学上的独立样本量。

# 6. 评价指标：为什么不能只给一个“准确率”

## 6.1 参考表面 residual

当前总账 \(n=1550\)：median 3.6 cm、p90 8.4 cm、p95 11.6 cm。历史 pre-fit ledger \(n=450\) median 9.3 cm，并存在巨大 outlier。

但这些数据来自不同批次、不同局部域，而且粗模本身参与重建，因此只能说“与同一摄影测量参考的内部一致程度”。

## 6.2 5 cm 筛查账本

149 个通过、101 个未通过，总计 250 个保留筛查项。通过率 59.6% **不是模型 accuracy，也不是重建 success rate**。它的价值在于：未通过项仍然可见，并继续驱动后续工作。

## 6.3 coverage gap

对选定高区定义：若粗模样本距部件模型大于 1m，则记为“当前未解释”。B25/B26 中这一比例从 78.8% 降到 14.6%。这个指标回答“还有多少明显占据没有被建出来”，和局部 residual 回答的是不同问题。

## 6.4 object / mesh reuse

37,153 objects / 3,916 mesh datablocks ≈ 9.5×，说明场景大量使用 shared mesh / collection instance。它不应被写成“效率提升 9.5 倍”或“压缩 9.5 倍”。

## 6.5 语义覆盖

station part map 当前覆盖 151 个设备；106 个官方名称中 76 个已挂接、30 个仍未挂接；100 个 12MZ 语义组挂到几何。

#1 主变试点：189 mesh → 26 part class；36 个官方巡视点位 = 31 model part + 4 external component + 1 non-visual。这里的“36/36 被分类”也不等于“全站所有巡视部件几何都已建完”。

# 8. 失败与恢复研究

![图 6：失败—诊断—修正—方法变化](../figures/fig05_failure_recovery.png)

## 8.1 B01→B02：验证器不仅否决几何，也修正指标定义

B01 的源资产哈希和变换复现都正常，但三只避雷器选定留出域 RMS 约 4.8/7.3/5.1cm，导致批次失败。项目没有把阈值调宽，而是保留失败并发现参考域混入附件突起。B02 重新定义拟合/留出区域，并明确说明新口径不能冒充“同指标精度提升”。

这说明 verifier 自身也是研究对象：**比较域选错，评价就会误导智能体。**

## 8.2 B15：错误不是参数，而是抽象层级

邻台污染使测量法失效，共享 spool 又被错误延伸到不同现场位置。多轮返工后，一部分母线段被从共享 MASTER 拆成 site-specific finite segment。

这说明组件库不是“能复用就复用”，而是一个需要证据支持的几何等价假设。

## 8.3 B36：高信息密度人工反馈

人工在俯视对照中只需要指出“这里缺了母线架”。系统随后完成：查历史代码 → 找到 B08 曾排除该结构的证据 → 新建批次 → 处理非有限路径失败 → 调整 0.16m 避让消防管 → 重读和接触检查。

这种 human-in-loop 的成本结构和传统手工建模不同：人负责指出错误，智能体负责长链条执行。

## 8.4 D38：从像素红框到世界坐标

![图 7：D38 人工标注纠错链](../figures/fig06_d38_human_feedback.png)

D38 evidence 将用户标注图与原 review 图做模板匹配（NCC 0.94/0.92、scale 0.94），再通过相机映射恢复 7 个标记区域的模型世界坐标。三组错误柜体共 9 个对象没有被删除，而是移入 quarantine；三处 GIS 缺口以及消防室/砂箱被补建。随后 D38.1 还出现过“把注册矩阵 yaw 当设备朝向”的语义错误，最终在 D38.2 修正。

这里最值得强调的是**纠错链的可追溯性**，而不是“最后画面对了”。

## 8.5 semantic v3：语义挂接也会“看起来合理但其实错”

早期 semantic mapping 结合名称/空间盒进行挂接，但隔离渲染和现场照片发现：跨间隔母线筒被算到错误 GIS，避雷器/开关语义混淆，部分接地刀闸和电容器语义被错误解释。v3 改成按设备族和结构规则审计，并允许“该台账设备当前无几何”作为合法状态。

这把 verifier 的思想从几何层延伸到语义层。

# 9. D40/D41：从展示层到巡检语义

## 9.1 D40 是一个有价值的不变性对照

D40 为钢构、导线、铝管、金具和瓷件分配 6 类 PBR 材质。验证器明确检查：D38 输入不被修改；对象/场景/集合/mesh 数一致；matrix_world 一致；总顶点数一致；只有材质层变化。

D40.1 还曾漏掉实例集合内部网格，D40.2 修改遍历方式。这说明“只改材质”也需要 verifier，而不是凭视觉判断。

## 9.2 D41 把部件语义真正并入站内实例

![图 8：D41 巡检附件层](../figures/fig07_d41_inspection_semantics.png)

# 10. 当前最需要补的科研实验

现在的历史记录已经足以写一篇有方法论和失败研究的技术论文，但还缺几类能显著增强说服力的实验。

### 10.1 模型/推理强度受控对比

未来选择若干固定局部任务（例如单个 GIS、主变附件、D38 风格纠错），冻结完全相同的证据包，分别用不同模型/推理强度重复，比较：完成率、validator reject 次数、返工次数、最终 residual、token、wall-clock 和人工介入。

### 10.2 专业人工基线

选择 2–3 个局部设备，给专业 Blender/CAD 人员完全相同的输入，记录达到同一验收口径的时间、操作次数和最终质量。这样才能讨论“智能体是否提升工程效率”。

### 10.3 独立 ground truth

使用全站仪、激光扫描或少量高可信控制点，建立与粗模独立的局部几何评测。只有这样才能从“内部参考 residual”升级到“绝对/独立精度”。

### 10.4 多站点复现

在至少第二座匿名站点重复同一 evidence compiler + MASTER/SITE + verifier 协议，区分“方法本身可迁移”和“智能体只是利用了单站点的长期历史”。

### 10.5 资源成本

参考 Astra embodied-policy 报告，把 token、推理调用次数、Blender 执行时长、验证时长、人工 review 时长作为一等指标；目前历史记录不足以可靠重建这些数据。

# 11. 结论

这套匿名站点数据真正有论文价值的部分，不是一个“AI 生成的漂亮 Blender 场景”，而是一个通用推理智能体在**异构证据、长期历史、反复失败、组件复用、确定性验证和稀疏人工反馈**共同约束下逐步形成工程模型的完整轨迹。

AstraBuild 的核心观点可以浓缩为：

> **不要相信模型生成；要把模型的每个空间假设变成可执行、可验证、可追溯、可拒绝的工程动作。**

这使“GPT-6 Astra 用 Blender 自动建模”从 demo 叙事升级为一个可研究的 agentic engineering system。下一阶段的重点不是继续堆更多效果图，而是冻结模型 provenance、补独立真值、做受控 agent/人工基线、多站点复现和资源成本统计。
